=== ¿Por qué los archivos son como son?

La forma en la que hoy en día organizamos nuestros archivos fue heredada de los primeros *sistemas operativos* que se adoptaron ampliamente en ambientes comerciales.

.Diferentes logos de sistemas operativos.
[#os-png]
image::01_Sesion/OSs.png[Diferentes logos de sistemas operativos,500,align=center]

Un *sistema operativo* es simplemente un entorno de utilidades muy grande que nos permite a nosotros dar ordenes al computador sin necesidad de hablar su idioma. Los sistemas operativos modernos siguen una convención heredada compartida para clasificar todos los archivos. Tomemos como ejemplo el siguiente archivo:

[source]
....
C:\Users\jrosas3\AppData\Local\Programs\Git\LICENSE.txt
....

Sus partes serían:

nombre completo:: `C:\Users\jrosas3\AppData\Local\Programs\Git\LICENSE.txt`
ruta:: `C:\Users\jrosas3\AppData\Local\Programs\Git`
nombre (corto):: `LICENSE.txt`
extension:: `txt`

=== ¿Qué es un comando?
Un *comando* es, como su nombre lo indica, una orden entregada por el usuario al computador. En Durante varios años y antes de las interfaces gráficas (GUI, graphical user interface) los comandos eran la forma más ampliamente usada en la que los usuarios interactuaban con los computadores. La forma de uso era que el computador se quedaba esperando hasta recibir un comando en lenguaje natural (texto) y una vez lo recibía procedía a interpretarlo y devolver lo que el usuario estaba pidiendo.

=== ¿Qué es la terminal de comandos?
La interfaz de comandos o CLI (Command-Line Interface) es la interfaz por la cual un sistema operativo o un aplicativo reciben comandos directamente del usuario. A día de hoy cada sistema operativo tiene al menos un CLI integrado.

== Git & el control de versiones

.Nombres peculiares de archivos.
[#file-naming]
image::01_Sesion/FileNaming.png[Nombres peculiares de archivos,600,align=center]

=== ¿En qué consiste el control de versiones?
Un *control de versiones* consiste registrar los cambios realizados en un archivo o conjunto de archivos a lo largo del tiempo, de modo que se puedan recuperar versiones específicas más adelante [<<r3>>].

=== ¿Qué es Git?
Git es el *sistema de control de versiones (VCS)* más ampliamente utilizado en la actualidad. La forma en la que Git registra los diferentes estados de los archivos a los que hace seguimiento es a través de "fotos". Si un estado de un archivo no ha cambiado de una foto a otra, no es necesario que git lo guarde de nuevo dentro de su trazabilidad interna.

.Esquema ilustrativo del funcionamiento de Git.
[#git-version-fundamentals]
image::01_Sesion/GitVersionsBasics.png[Esquema ilustrativo del funcionamiento de Git,600,align=center]

IMPORTANT: Git está pensado para llevar un control de versiones de archivos de texto plano o que puedan ser interpretados como texto plano. Usarlo para versionar archivos binarios puede llevar a un alto consumo de memoria y una ralentización del proceso.

=== Estados de archivos en Git
Git tiene tres estados principales en los que se pueden encontrar los archivos:

Confirmado (commited):: Significa que los datos están almacenados de manera segura en la base de datos local donde Git administra el *repositorio*.
Modificado (modified):: Significa que se ha modificado el archivo pero todavía no se ha confirmado a la base de datos.
Preparado (staged):: Significa que se ha marcado un archivo modificado en su versión actual para que vaya en la próxima confirmación.

TIP: Existen otros estados pero los tres mencionados son los principales y alrededor de los cuales se estructura Git.

=== Escenarios de Git
Existen tres secciones principales de un proyecto de Git:

El directorio de Git (Git directory):: Es donde se almacena, entre algunas otras cosas, la base de datos local donde Git administra el *repositorio*. Es la parte más importante de Git.
El directorio de trabajo (working directory):: Es una copia de una versión del proyecto. Estos archivos se sacan de la base de datos comprimida en el directorio de Git, y se colocan en disco para que se puedan usar o modificar.
El área de preparación (staging area):: Es un archivo, generalmente contenido en el directorio de Git, que almacena información acerca de lo que va a ir en la próxima confirmación(commit).

== Flujo de trabajo con Git

.Flujo de trabajo básico con Git
[#git-workflow-diagram]
plantuml::{diagramsdir}/01_GitBasicWorkflow.puml[format=svg, alt="Flujo de trabajo básico con Git", align="center"]

Tal y cómo se muestra en <<git-workflow-diagram>>, la forma más básica de trabajar con Git consiste en 4 pasos cíclicos:

#1: Creación del repositorio:: Paso en el cual se le dice a Git que cree el respositorio para el control de versiones en una ruta deseada.

#2: Modificación de archivos:: En este paso es donde pasamos la mayor parte del tiempo. Aquí se crean, eliminan y/o actualizan los archivos que queremos considerar dentro del control de versiones.

#3: Registro de modificaciones:: En este paso se corren todos los comandos necesarios para indicarle a Git que registre las modificaciones que nos interesan.

#4: Revisión de modificaciones:: En este paso utilizamos todas las herramientas que ofrece git para poder revisar y tener la posibilidad de corregir cualquier modificación que se haya registrado en el repositorio.

=== Creación de repositorio
Cuando hablamos de repositorio, en el ámbito de Git, nos referimos a toda la estructura de archivos que permite a Git realizar un control de versiones sobre ciertos archivos que se le indican. Por lo tanto, si no existe un repositorio tampoco existe un control de versiones. Sin embargo, eso no quiere decir que no existan los archivos que queremos versionar, sino que no se ha iniciado su control de versiones.

Hay en total dos formas de crear un repositorio en Git:

1. Convertir una ruta local en un repositorio nuevo.
2. Importar un repositorio desde una fuente externa.

Debido al alcance de esta primera sesión, nos centraremos en la primera forma. Para esto basta con abrir cualquier terminal dentro de la ruta de la carpeta raíz de los archivos que se quieren versionar. Para esto:

1. Abrimos la terminal y nos dirigimos a la ruta de la carpeta raíz así: `cd "<ruta_carpeta_raíz>"`. En donde `<ruta_carpeta_raíz>` es la ruta donde tenemos los archivos que queremos versionar.

2. Inicializamos git dentro de la carpeta con el siguiente comando: `git init`.

NOTE: Tenga en cuenta que el repositorio creado "registra" todo el contenido de la carpeta en un solo lugar. Es decir, si dentro de la carpeta existieran otras dos llamadas `proyecto_1` y `proyecto_2`, todos los cambios que ocurran dentro de una de ellas van a afectar las versiones de la otra, sin importar si son independientes o no.

=== Modificación de archivos
La creación, eliminación y/o modificación de los archivos dentro de un repositorio depende del propósito de cada persona y proyecto. Sin embargo, la mayoría de veces no es recomendable llevar un control de versiones de todos los archivos que se encuentren dentro de la carpeta del repositorio. Para esto existe un archivo especial de Git llamado `.gitignore`.

Tal y como su nombre sugiere, el archivo `.gitignore` le indica a Git que archivos dentro de la carpeta actual debe ignorar. Típicamente en este archivo se listan todos los archivos binarios que se encuentren en la carpeta. Sin embargo, cada proyecto tiene sus propias necesidades y lo más aconsejable es buscar referencias y ejemplos de archivos `.gitignore` según los lenguajes de programación y tecnologías que se estén usando en el proyecto. link:https://www.toptal.com/developers/gitignore[gitignore.io] y link:https://mrkandreev.name/snippets/gitignore-generator/[gitignore-generator] son dos páginas de referencia que se pueden usar.

=== Registro de modificaciones (Stage y Commit)
Durante del registro de modificaciones se corren todos los comandos necesarios para que el estado actual de uno o varios archivos quede registrado dentro del repositorio de Git.

.Flujo de trabajo normal con un archivo que se desea versionar.
[#git-file-workflow]
image::01_Sesion/GitFileWorkflow.png[Flujo de trabajo normal con un archivo que se desea versionar,700,align=center]

En <<git-file-workflow>> se encuentran todos los movimientos que normalmente se realizan sobre un archivo a la hora de versionar con Git:

Untracked -> Staged:: Cuando se crea un repositorio desde cero en una ruta local. Todos los archivos dentro de este se encontraran marcados como _untracked_ (sin rastrear). Lo cual indica que aún no se encuentran siendo "observados" por el repositorio de git. Para que estos pasen a ser marcados cómo _tracked_ (rastreados) tienen que haber sido agregados al escenario de preparación (_stage_). Para esto se ejecuta el siguiente comando: +
`git add <archivo>` o `git add .` +
Con el primer comando se agrega únicamente el archivo al escenario de preparación y con el segundo se agregan todos los archivos sin rastrear y modificados. Se debe tener en cuenta que `<archivo>` es el nombre completo del archivo incluyendo su extensión.

Staged -> Unmodified:: La forma de registrar una nueva version de un archivo es a través de _commits_ (confirmaciones). Esto lo que hace es registrar los cambios guardados en el escenario de preparación dentro del repositorio de Git. Para esto se ejecuta el siguiente comando: +
`git commit -m "mensaje"` +
Se aconseja que el mensaje sea lo más claro e indicativo posible sobre los cambios que se hicieron.

Unmodified -> Modified:: Este movimiento representa los cambios que se le hacen a un archivo que ya se encuentra rastreado y que ya tienen al menos un cambio confirmado.

Modified -> Staged:: Este movimiento es similar al primero y representa la agregación de un archivo que ha sido modificado al escenario de preparación. Para esto se ejecuta el mismo comando: +
`git add <archivo>` o `git add .`

=== Revisión de modificaciones
Para ver el historial de registros o _commits_ con sus respectivos mensajes, autores y fechas Git proporciona el siguiente comando: `git log`. Este comando muestra los _commits_ en la terminal sin embargo hay formas de verlos más gráficamente utilizando aplicaciones de terceros que veremos en la siguiente sección.
